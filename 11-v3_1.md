# DD API V3.1 (Optioneel)

V3.1 is een optionele uitbreiding op DD API V3 met vier onafhankelijke extensies:

- **[PubSub](#pubsub)** — Notificaties bij wijzigingen in observaties
- **[Zoekprofielen](#zoekprofielen)** — Herbruikbare query-templates
- **[Resultaatprofielen](#resultaatprofielen)** — Response transformaties
- **[Batch Mutations](#batch-mutations)** — Create, update en delete operaties

Alle extensies zijn beschikbaar via de standaard v3-endpoints (onder `/v3/`).

## Capabilities discovery

Servers geven via de `X-DD-Capabilities` header aan welke extensies worden ondersteund:

```http
X-DD-Capabilities: searchprofiles,resultprofiles,observations-cud
```

**Mogelijke waarden:**
- `searchprofiles` — Zoekprofielen
- `resultprofiles` — Resultaatprofielen
- `pubsub` — PubSub (zonder WebSub)
- `pubsub,websub` — PubSub met WebSub mapping
- `observations-cud` — Mutaties voor observaties
- `references-cud` — Mutaties voor references

Waarden worden komma-gescheiden opgegeven.

## Pas-Toe-Of-Leg-Uit (PTOLU)

DD API V3.1 volgt waar mogelijk de [API Design Rules](https://publicatie.centrumvoorstandaarden.nl/api/adr/).

**Afwijkingen en motivaties per extensie:**

| Extensie               | Richtlijn                | Status            | Toelichting                                                                                                                                                                                                                       |
|------------------------|--------------------------|-------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **PubSub**             | REST stateless           | ❌ Afwijking       | Introduceert server-side state (subscriptions, threshold tracking). Dit is inherent aan event-driven architecturen. State wordt volledig server-side beheerd; elke subscription is een zelfstandige resource met eigen lifecycle. |
|                        | AsyncAPI                 | ⚠️ Niet toegepast | AsyncAPI is (per 2026) nog niet opgenomen in de standaardenlijst van het Kennisplatform API's. DD API V3.1 gebruikt daarom een HTTP REST-gebaseerde subscription API.                                                             |
| **Zoekprofielen**      | REST stateless           | ✅ Conform         | Volledig stateless; profielen zijn read-only resources.                                                                                                                                                                           |
|                        | Caching                  | ✅ Conform         | Responses zijn cacheable via standaard HTTP cache headers.                                                                                                                                                                        |
| **Resultaatprofielen** | REST stateless           | ✅ Conform         | Volledig stateless transformatie.                                                                                                                                                                                                 |
|                        | Content negotiation      | ✅ Conform         | Gebruikt standaard `Accept` header mechanisme.                                                                                                                                                                                    |
|                        | Query parameter fallback | ✅ Conform         | Voor clients die headers niet kunnen aanpassen (bijv. browsers).                                                                                                                                                                  |
| **Batch Mutations**    | HTTP methods             | ✅ Conform         | POST voor batch operations, standaard authenticatie.                                                                                                                                                                              |
|                        | Authenticatie            | ✅ Conform         | Volgt bestaande DD API V3 authenticatie-mechanismen.                                                                                                                                                                              |

**Motivatie PubSub stateless-afwijking:**
Event-driven notificaties vereisen server-side state voor subscriptions en threshold tracking. De alternatieve oplossing (client moet continu pollen) is inefficiënt en schaalt niet. PubSub is daarom een bewuste, pragmatische afwijking voor real-time use cases.

**Motivatie AsyncAPI:**
AsyncAPI is een logische fit voor event-driven APIs, maar is (per februari 2026) nog niet opgenomen in de standaardenlijst van het Kennisplatform API's. Zelfs OpenAPI Specification 3.1 is nog in afwachting van adoptie. Gezien deze adoptie-snelheid wordt verwacht dat AsyncAPI-acceptatie nog jaren kan duren. DD API V3.1 kiest daarom voor een pragmatische HTTP REST-gebaseerde subscription API met optionele WebSub-mapping voor interoperabiliteit met bestaande pub/sub-infrastructuur. Mocht AsyncAPI op termijn worden geaccepteerd, dan kan een toekomstige versie (V4+) hierop overstappen zonder breaking changes in de huidige functionaliteit.

**Motivatie Zoekprofielen:**
OData biedt geen native mechanisme voor herbruikbare filter-templates. `searchprofile` vult deze leemte op een backwards-compatible manier zonder kernfunctionaliteit te breken.

**Algemene naleving:**
- ✅ Versionering via `API-Version` header
- ✅ Capabilities discovery via `X-DD-Capabilities`
- ✅ HTTP status codes conform RFC 7231
- ✅ OData error-formaat voor foutmeldingen
- ✅ HTTPS verplicht voor productie-omgevingen

# PubSub

<aside class="advisement" title="Status: In ontwikkeling">
Deze sectie is onderdeel van de V3.1 concept-specificatie. Implementatie wordt aangemoedigd voor testdoeleinden, maar de interface is nog niet bevroren.
</aside>

<aside class="note" title="REST en State">
PubSub introduceert **server-side state** (subscriptions, threshold tracking) en is daarom **niet stateless**. Dit wijkt af van de REST-principes en de Kennisplatform API's-richtlijnen. De state wordt echter volledig server-side beheerd en wordt niet gedeeld tussen client en server buiten de expliciete subscription-resources om. Elke subscription is een **zelfstandige resource** met eigen lifecycle, conform REST resource-oriented design.
</aside>

## Inleiding

De Pub/Sub-extensie voor DD API V3 stelt clients in staat zich te abonneren op nieuwe of gewijzigde `Observation` resources via verschillende leveringsmethoden.

Een server die deze extensie ondersteunt, **MOET** de `API-Version` header met waarde `3.1.0` meesturen en de `X-DD-Capabilities` header **MOET** ten minste de waarde `pubsub` bevatten.

## Terminologie

- **Subscription (abonnement)** — Een server-beheerde resource die aangeeft welke gebeurtenissen een client wil ontvangen.
- **Trigger** — Een OData-gebaseerde conditie (filter) die bepaalt wanneer een melding wordt gegenereerd.
- **Delivery Method (leveringsmethode)** — De techniek waarmee meldingen worden afgeleverd (SSE, push, MQTT, etc.).
- **Event** — Een melding die Observation-data bevat conform het Observation model.

## Content Negotiation (leveringsmodel)

Clients en servers kunnen de gewenste leveringsmethode onderhandelen via specifieke headers, vergelijkbaar met het CRS-onderhandelingsmechanisme in DD API V3.

**Request headers:**
```http
Accept-DeliveryMethod: sse, push, mqtt
```

**Response headers:**
```http
Content-DeliveryMethod: sse
```

## Resources

Alle PubSub-endpoints zijn gepositioneerd onder `/v3/` om ze te onderscheiden van de reguliere OData-resources.

### GET /v3/subscriptions

Geeft een overzicht van de actieve abonnementen van de huidige geauthenticeerde gebruiker.

### POST /v3/subscriptions

Maakt een nieuw abonnement aan. De server genereert een uniek id en een verloopdatum (expiresAt).

**Request body:**

```json
{
  "delivery": {
    "method": "push",
    "endpoint": "https://callback.example.com/events",
    "secret": "uw-geheime-sleutel"
  },
  "trigger": {
    "filter": "Parameter/Compartment eq 'OW' and Result/Value gt 2.0",
    "select": "Id, ResultTime, Result/Value"
  }
}
```

**Response (201 Created):**

```json
{
  "id": "sub-550e8400-e29b",
  "status": "active",
  "expiresAt": "2024-02-05T12:00:00Z",
  "delivery": {
    "method": "push",
    "endpoint": "https://callback.example.com/events",
    "qos": "at-least-once"
  },
  "trigger": {
    "filter": "Parameter/Compartment eq 'OW' and Result/Value gt 2.0",
    "select": "Id, ResultTime, Result/Value"
  }
}
```

**HTTP status codes:**

- `201 Created` — Succesvol aangemaakt
- `400 Bad Request` — De trigger-expressie (filter) bevat syntaxisfouten of de leveringsmethode is onvolledig geconfigureerd
- `401 Unauthorized` — Authenticatie is verplicht voor het beheren van abonnementen
- `403 Forbidden` — De gebruiker heeft geen rechten op de resources die in de trigger worden gefilterd
- `406 Not Acceptable` — De server ondersteunt de gevraagde leveringsmethode uit de `Accept-DeliveryMethod` header niet
- `429 Too Many Requests` — De server weigert het abonnement omdat het maximum aantal toegestane abonnementen voor deze gebruiker is bereikt

## Abonnement Lifecycle

**Verloopdatum:**
Elk abonnement heeft een `expiresAt`. De client moet het abonnement verlengen via een PATCH request voordat deze datum is bereikt. Verlopen abonnementen worden door de server verwijderd.

**Status:**
- `active` — Gebeurtenissen worden verwerkt en verzonden
- `suspended` — De levering is tijdelijk stopgezet (bijv. na herhaalde afleverfouten naar een push-endpoint)

## Trigger Model

De trigger bepaalt welke observaties tot een event leiden. Het maakt gebruik van de standaard OData `$filter` syntax.

| Veld       | Type    | Omschrijving                                                                |
|------------|---------|-----------------------------------------------------------------------------|
| filter     | string  | Verplicht. Een OData expressie toegepast op de Observation.                 |
| select     | string  | Optioneel. Een OData $select om de event-payload te beperken.               |
| on         | string  | Optioneel. Type gebeurtenis: `created`, `updated`, `deleted`, `threshold`.  |
| threshold  | object  | Optioneel. Alleen bij `on=threshold`: drempel voor een waarde-overgang.     |
| latestOnly | boolean | Optioneel. Alleen de meest recente observation in de gefilterde set sturen. |
| latestBy   | string  | Optioneel. `resultTime` of `phenomenonTime` (default `resultTime`).         |
| message    | object  | Optioneel. Bericht-template voor notificaties.                              |

**Normatieve regels:**

- Als `on` ontbreekt, **MOET** de server dit interpreteren als `created`
- Bij `on=updated` **MOET** de server een event genereren wanneer `Metadata/ModifiedOn` wijzigt voor een Observation die aan `filter` voldoet
- Bij `on=threshold` **MOET** `threshold` aanwezig zijn
- Als `latestBy` ontbreekt, **MOET** de server `resultTime` gebruiken
- Als `latestOnly` waar is, **MOET** de server uitsluitend de meest recente Observation uit de door `filter` bepaalde set opnemen
- Triggers **MOETEN** worden beoordeeld op basis van de huidige resource-staat en `Metadata/ModifiedOn`; correcties **KUNNEN** daardoor een `updated`-event genereren

**Threshold object:**

| Veld      | Type   | Omschrijving                                                                   |
|-----------|--------|--------------------------------------------------------------------------------|
| field     | string | Verplicht. Veldpad, bijv. `Result/Value`.                                      |
| operator  | string | Verplicht. Een van: `gt`, `ge`, `lt`, `le`, `eq`, `ne`.                        |
| value     | number | Verplicht. Drempelwaarde.                                                      |
| direction | string | Optioneel. `up` = overschrijden, `down` = terug onder drempel, `both` = beide. |

### Voorbeelden

**Drempel overschreden:**

```json
{
  "trigger": {
    "on": "threshold",
    "threshold": {
      "field": "Result/Value",
      "operator": "gt",
      "value": 2.5,
      "direction": "up"
    },
    "filter": "Parameter/Quantity eq 'WATHTE' and Foi/Code eq 'AMSLOTRK'",
    "select": "Id, ResultTime, Result/Value, Foi/Code"
  }
}
```

**Alleen nieuwste waarde voor een specifieke locatie + parameter:**

```json
{
  "trigger": {
    "filter": "Parameter/Quantity eq 'WATHTE' and Foi/Code eq 'AMSLOTRK'",
    "latestOnly": true,
    "latestBy": "resultTime",
    "select": "Id, ResultTime, Result/Value, Foi/Code"
  }
}
```

**Bericht-template:**

Als een client een eigen notificatiebericht wil laten meesturen, kan `message` worden gebruikt. De server **MAG** placeholders in de template vervangen met velden uit de payload (bijv. `{Result/Value}` of `{Foi/Code}`). Onbekende placeholders **MOETEN** ongemoeid worden gelaten.

**Message object:**

| Veld  | Type   | Omschrijving                       |
|-------|--------|------------------------------------|
| title | string | Optioneel. Titel van het bericht.  |
| body  | string | Verplicht. Tekst met placeholders. |

**Voorbeeld:**

```json
{
  "trigger": {
    "filter": "Result/Value gt 2.5 and Parameter/Quantity eq 'WATHTE'",
    "message": {
      "title": "Waarschuwing waterhoogte",
      "body": "Waterhoogte {Result/Value} bij {Foi/Code} op {ResultTime}"
    }
  }
}
```

## WebSub mapping

Voor WebSub-compatibele hubs **MOET** een subscription request minimaal de velden `hub.mode`, `hub.topic` en `hub.callback` bevatten. DD-API specifieke trigger-informatie **MOET** in de request body worden opgenomen als extra velden.

**Verplichte velden (WebSub):**

- `hub.mode`: `subscribe`
- `hub.topic`: URL van het OData-collection endpoint (bijv. `/v3/odata/observations`)
- `hub.callback`: callback-URL van de client

**DD-API extensievelden (payload):**

- `dd.trigger.filter`
- `dd.trigger.select`
- `dd.trigger.on`
- `dd.trigger.threshold.field`
- `dd.trigger.threshold.operator`
- `dd.trigger.threshold.value`
- `dd.trigger.threshold.direction`
- `dd.trigger.latestOnly`
- `dd.trigger.latestBy`
- `dd.trigger.message.title`
- `dd.trigger.message.body`

**Voorbeeld (x-www-form-urlencoded):**

```http
POST /hub
Content-Type: application/x-www-form-urlencoded

hub.mode=subscribe&
hub.topic=https%3A%2F%2Fapi.example.com%2Fv3%2Fodata%2Fobservations&
hub.callback=https%3A%2F%2Fclient.example.com%2Fwebsub%2Fcallback&
dd.trigger.on=threshold&
dd.trigger.threshold.field=Result%2FValue&
dd.trigger.threshold.operator=gt&
dd.trigger.threshold.value=2.5&
dd.trigger.threshold.direction=up&
dd.trigger.filter=Parameter%2FQuantity%20eq%20'WATHTE'&
dd.trigger.select=Id%2C%20ResultTime%2C%20Result%2FValue
```

**Voorbeeld (JSON body, indien ondersteund):**

```http
POST /hub
Content-Type: application/json

{
  "hub": {
    "mode": "subscribe",
    "topic": "https://api.example.com/v3/odata/observations",
    "callback": "https://client.example.com/websub/callback"
  },
  "dd": {
    "trigger": {
      "on": "threshold",
      "threshold": {
        "field": "Result/Value",
        "operator": "gt",
        "value": 2.5,
        "direction": "up"
      },
      "filter": "Parameter/Quantity eq 'WATHTE'",
      "select": "Id, ResultTime, Result/Value"
    }
  }
}
```

# Zoekprofielen

<aside class="advisement" title="Status: In ontwikkeling">

</aside>

## Inleiding

Zoekprofielen maken het eenvoudiger om complexe selecties te maken. Een zoekprofiel beschrijft een vooraf gedefinieerde selectie van observaties op basis van filters en geselecteerde velden.

Een voorbeeld hiervoor is Slim Watermanagement, dat een standaard selectie van waterstanden en stromingen wil aanbieden voor hun gebruikers.

Een server die deze extensie ondersteunt, **MOET** de `API-Version` header met waarde `3.1.0` meesturen en de `X-DD-Capabilities` header **MOET** ten minste de waarde `searchprofiles` bevatten.

## Concept

Een zoekprofiel bepaalt **alleen** filters en selecties uit het Parameter-blok. Het FoI (Feature of Interest, in DD API V3 altijd de meetlocatie) en de tijdsperiode worden altijd door de gebruiker opgegeven.

**Logische verwerking:**

Logisch gezien wordt een zoekprofiel toegepast vóórdat de query wordt uitgevoerd. Additionele filters en selecties opgegeven in de query door de gebruiker, worden toegepast op de resultaten van het zoekprofiel.

- **Filter:** `((zoekprofiel) AND ($filter))`
- **Select:** Velden uit zoekprofiel + velden uit `$select`

## Endpoint

```http
GET /v3/searchprofiles
```

**Response:**

```json
{
  "value": [
    {
      "id": "FC-TR-SWM",
      "name": "Slim Watermanagement Tijdreeksen (Fysisch/Chemisch)",
      "description": "Selectieprofiel voor Slim Watermanagement met waterstanden en stromingen.",
      "parameterFilterEquivalent": "(parameter/quantity in ('Cl/GELDHD','Q','DEBFTE','GELDHD','SALNTT','T','DRSTRPBSTTPE','WATHTE','STROOMSHD') or (parameter/quantity eq 'CONCTTE' and parameter/parameter eq 'Cl')) and parameter/compartment eq 'OW'",
      "parameterSelect": "phenomenonTime, resultTime, foi/Code, foi/Geography, parameter/quantity, parameter/parameter, result/measure/uom, result/measure/value"
    }
  ]
}
```

## Toepassing in Queries

Een client past een zoekprofiel toe door de unieke `id` mee te geven in de `searchprofile` query parameter (zonder `$`-prefix, want het is geen OData system query option).

**Voorbeeld:**

```http
GET /v3/odata/observations?searchprofile=FC-TR-SWM&$filter=ResultTime ge 2024-01-01T00:00:00Z
```

## Verwerkingsregels

De server **MOET** de volgende regels toepassen:

1. **Filter Samenvoeging:** De server **MOET** het filter uit het zoekprofiel (`parameterFilterEquivalent`) combineren met het eventuele `$filter` van de gebruiker middels een logische `AND` operatie.

2. **Select Samenvoeging:** De server **MOET** de velden uit `parameterSelect` combineren met de velden uit de `$select` van de gebruiker. Indien de gebruiker geen `$select` opgeeft, worden de velden uit het zoekprofiel als basis gebruikt.

3. **Meerdere Profielen:** Indien meerdere profielen worden opgegeven (bijv. `searchprofile=P1,P2`), worden de filters van deze profielen gecombineerd middels een logische `OR`. Het resultaat daarvan wordt vervolgens met `AND` gekoppeld aan het filter van de gebruiker.

## Foutafhandeling

Indien een client een `searchprofile` opgeeft dat niet bestaat, **MOET** de server antwoorden met een **HTTP 400 Bad Request**, met een duidelijke foutmelding in het OData error-formaat.

## Optimalisatie (Informatief)

Zoekprofielen bieden server-ontwikkelaars de mogelijkheid om de performance van de API aanzienlijk te verbeteren:

- **Pre-compilatie:** De server kan de OData-expressie in een zoekprofiel vooraf valideren en vertalen naar een geoptimaliseerde database-query.
- **Indexering:** Door bekende zoekprofielen te analyseren, kunnen gerichte database-indexen worden aangelegd voor de meest gebruikte combinaties van parameters en grootheden.
- **Caching:** Resultaten van veelgebruikte zoekprofielen kunnen door de server effectiever worden gecachet, wat de responstijden voor eindgebruikers verlaagt.

# Resultaatprofielen

<aside class="advisement" title="Status: In ontwikkeling">

</aside>

## Inleiding

Standaard bepaalt de server de optimale representatie (losse meting of tijdreeks) van het Result. In V3.1 kan een client dit forceren.

Een server die deze extensie ondersteunt, **MOET** de `API-Version` header met waarde `3.1.0` meesturen en de `X-DD-Capabilities` header **MOET** ten minste de waarde `resultprofiles` bevatten.

## Opties

### Optie 1: Content Negotiation

Een client **MAG** via de `Accept` header een specifiek profiel afdwingen:

- `Accept: application/json;resultprofile=original` (Geen aanpassing)
- `Accept: application/json;resultprofile=coveragejson` (Forceert tijdreeksen)
- `Accept: application/json;resultprofile=observation` (Forceert losse observaties)

### Optie 2: Query Parameter

Indien headers niet bruikbaar zijn, **MAG** de parameter `resultprofile` worden gebruikt:

- `?resultprofile=original`
- `?resultprofile=coveragejson`
- `?resultprofile=observation`

## Verwerkingsregels

- Indien een server de gevraagde transformatie niet kan uitvoeren, **MOET** deze antwoorden met een **406 Not Acceptable**.
- Indien de aanvrager een `resultprofile` heeft gebruikt, **MOET** dat ook in een response header worden teruggegeven.

# Batch Mutations

<aside class="advisement" title="Status: In ontwikkeling">
Deze sectie is onderdeel van de V3.1 concept-specificatie. Implementatie wordt aangemoedigd voor testdoeleinden, maar de interface is nog niet bevroren.
</aside>

## Inleiding

Deze extensie laat het toe om observations en references te muteren (toevoegen, wijzigen of verwijderen). Er is gekozen voor een batch-gebaseerde aanpak.

Binnen de batch kunnen individuele entiteiten worden toegevoegd, gewijzigd of verwijderd. De batch wordt **atomisch** verwerkt: als één operatie faalt, wordt de hele batch teruggerold. Dit zorgt voor consistentie en vereenvoudigt foutafhandeling.

**Rationale voor batches:**

Bij het muteren van observaties moet vaak tegen meerdere domeintabellen worden gevalideerd. Batches stellen het verwerkende systeem in staat om efficiëntere validatie- en cache-strategieën toe te passen en de overhead van individuele requests te verminderen. Dit is vooral belangrijk voor **nalevering** van ecologische data, waar grote hoeveelheden observaties achteraf worden aangeleverd.

## Authenticatie en autorisatie

Batch-endpoints volgen dezelfde authenticatie- en autorisatiemechanismen als de reguliere DD API V3 endpoints.

**Ondersteunde authenticatiemethoden:**

De server **MOET** ten minste één van de volgende authenticatiemethoden ondersteunen:
- OAuth 2.0 / OpenID Connect
- Mutual TLS (mTLS)
- API keys

**Autorisatie:**

- De server **MOET** voor elke operatie in de batch controleren of de client geautoriseerd is
- Bij `create` **MOET** de client schrijfrechten hebben op de betreffende resource
- Bij `update` **MOET** de client schrijfrechten hebben op de specifieke observatie/reference
- Bij `delete` **MOET** de client verwijderrechten hebben op de specifieke observatie/reference
- Als de client voor één operatie niet geautoriseerd is, **MOET** de hele batch worden geweigerd (all-or-nothing)

**HTTP status codes gerelateerd aan authenticatie en autorisatie:**

- **401 Unauthorized** — Authenticatie ontbreekt of is ongeldig
- **403 Forbidden** — Client is geauthenticeerd, maar niet *geautoriseerd* voor één of meer operaties in de batch

## Observations

### GET /v3/observations/{id}

Haalt de inhoud van de specifieke observatie op.

Wanneer het item bestaat en toegang is geaccepteerd, dan zal een response worden teruggegeven in de vorm van een `Observation` conform het datamodel. Wanneer het item niet bestaat, dan zal een `404 Not Found` worden teruggegeven.

**HTTP status codes:**

- **200 OK** — De observatie bestaat en wordt geretourneerd in de response-body
- **400 Bad Request** — Syntactisch ongeldig verzoek
- **401 Unauthorized** — Authenticatie ontbreekt of is ongeldig
- **403 Forbidden** — Geen rechten om deze observatie te bekijken
- **404 Not Found** — Er bestaat geen observatie met de opgegeven Id

### POST /v3/observations/batch

Met dit request worden één of meerdere observations toegevoegd, gewijzigd of verwijderd. 
Hier geldt het **all-or-nothing principe**: als één operatie mislukt, mislukt de hele batch en worden geen wijzigingen doorgevoerd.
Wanneer de aanvrager en de implementatie observaties moeten 'koppelen', dan kan daarvoor een eigenschap `sourceId` worden gebruikt. 
Die eigenschap zit op item-niveau, niet op batch-niveau (zie onderstaand JSON voorbeeld). Die wordt bij een geslaagde `create` teruggestuurd.
Deze eigenschap is optioneel en heeft geen functionele betekenis voor de server, maar kan door de aanvrager worden gebruikt om tijdelijke identifiers te koppelen binnen de batch. 
De server **MOET** deze eigenschap onveranderd teruggeven in de response.

De server **MAG** kiezen tussen synchrone of asynchrone verwerking. Bij asynchrone verwerking wordt `202 Accepted` geretourneerd en kan de status later worden opgevraagd.

**Request body:**

```json
{
  "info": {
    "supplier": "RWS-WVL",
    "project": "MWTL-2024-Q1",
    "description": "Nalevering ecologie week 5"
  },
  "requests": [
    {
      "operation": "create",
      "sourceId": "<KeyInSourceSystem>",
      "observation": {
        "Id": "",
        "ResultTime": "2024-01-01T12:00:00Z",
        "Parameter": {
          "Quantity": "WATHTE",
          "Compartment": "OW"
        },
        "Result": {
          "Measure": {
            "Value": 2.5,
            "Uom": "m"
          }
        }
      }
    },
    {
      "operation": "update",
```

## Error Model

Lijst (geen dictionary) met foutmeldingen in de vorm van error-objecten, geproduceerd door de batch mutations extensie.

Het algemene formaat van een error-object is:

```json
{
  "Property": "property.path",
  "ErrorType": "ErrorTypeName",
  "Message": "Beschrijvende foutmelding"
}
```

Hierbij is `Property` de volledige naam van de property, zoals bijvoorbeeld `metadata.modifiedOn` of `phenomenonTime.beginPosition` of `result.measure.value`.

**ErrorType waarden:**

- `InvalidValue` — De waarde is syntactisch geldig, maar inhoudelijk niet toegestaan voor deze property (bijvoorbeeld een onbekende Aquo-code)
- `UnknownProperty` — De property komt niet voor in het DD API V3-datamodel
- `UnsupportedProperty` — Het systeem ondersteunt de opgegeven property niet
- `ValueOutOfRange` — De waarde ligt buiten het toegestane bereik voor deze property (bijvoorbeeld buiten een minimum/maximum)
- `MissingRequiredProperty` — Een verplichte property ontbreekt in de payload
- `InvalidFormat` — De syntaxis of representatie van de waarde is ongeldig (bijvoorbeeld geen geldige ISO8601-datum)
- `BusinessRuleViolation` — Een domein- of contextregel wordt overtreden, vaak op basis van de combinatie van meerdere properties
- `Duplicate` — Er komt een dubbele combinatie voor waar uniciteit vereist is (bijvoorbeeld dubbele parametercombinatie binnen één observatie)
- `NotAuthorised` — De client is niet geautoriseerd de gevraagde wijziging uit te voeren
- `InUse` — Het item kan niet verwijderd worden omdat het in gebruik is

**Normatieve regels:**

Deze fouten worden gebruikt door de batch mutations extensie om requests te valideren. Requests met één of meer fouten **MOGEN NIET** worden geaccepteerd als geldige entiteit; de server **MOET** in dat geval een HTTP 422 Unprocessable Entity teruggeven met een `errors`-array per gefaalde request.

Het is nadrukkelijk niet de bedoeling om observaties met fouten via DD API V3 aan afnemers aan te bieden.

**Voorbeeld van een foutrespons:**

```json
{
  "errors": [
    {
      "Property": "metadata.modifiedOn",
      "ErrorType": "InvalidFormat",
      "Message": "Waarde moet een geldige ISO8601-datum/tijd zijn."
    },
    {
      "Property": "result.measure.value",
      "ErrorType": "ValueOutOfRange",
      "Message": "Waarde ligt buiten het toegestane bereik voor deze grootheid."
    },
    {
      "Property": "parameter.observationType",
      "ErrorType": "InvalidValue",
      "Message": "Onbekende Aquo-code voor ObservationType."
    },
    {
      "Property": "parameter.observationType",
      "ErrorType": "BusinessRuleViolation",
      "Message": "De combinatie van ObservationType en Quantity is niet toegestaan volgens Aquo."
    },
    {
      "Property": "phenomenonTime.beginPosition",
      "ErrorType": "BusinessRuleViolation",
      "Message": "De PhenomenonTime.BeginPosition is later dan PhenomenonTime.EndPosition."
    }
  ]
```
